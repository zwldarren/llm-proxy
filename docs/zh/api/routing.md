# 虚拟模型与路由

开启智能路由后，会多出三个可用的模型名。它们不是真实模型：代理会在进程内对每个请求
分类，挑选一个具体已配置的模型来承接。启用[路由判定器](#routing-judge)时，模糊的首轮
请求可能还会额外向判定器模型发一次短暂的进程外调用；该功能默认关闭，刚打开时会先以
影子模式运行。

| 虚拟模型 | 取向 |
| --- | --- |
| `fast` | 最便宜且够用的模型，成本优先 |
| `auto` | 平衡（默认偏向） |
| `best` | 质量优先，成本次要 |

名称不区分大小写。`GET /v1/models` 会以 `"provider": "routing"` 列出它们。

## 启用

需要同时满足两个条件：

1. 设置 → 高级 → 智能路由 → 已启用（`server_config.smart_routing`）。
2. 至少有一条模型记录带 **`auto_eligible: true`**：只有这些模型会进入候选池。

然后把这个池配置好：

| 字段 | 为什么重要 |
| --- | --- |
| `auto_eligible` | 是否属于路由池（默认 false） |
| `quality_tier` | `economy` / `balanced` / `premium`；缺失或非法按 `economy` 计 |
| `context_length` | 估算的输入 + 最大输出装不下时，该候选被排除 |
| `supports_images` | 含图像内容的请求必需 |
| `routing_assignments` | 把模型限定到特定模式（`["fast","auto"]`）；不设表示所有模式 |
| 定价 | 预测成本是主要的评分信号 |

如果开启了智能路由但没有可用模型，`auto`/`fast`/`best` 会以配置错误失败，并在错误里
点名问题所在。

## 请求如何分类

这组信号在进程内投票，共两个。[路由判定器](#routing-judge)不参与投票，启用它也不会
改变下表的权重。在判定器适用的区间内，它的结论会替换信号组合的结果；区间之外不会调用
判定器（ADR-0018）。

| 信号 | 权重 | 来源 |
| --- | --- | --- |
| 元数据 | 0.50 | 请求形态（工具使用、图像、最大 Token、模型提示） |
| 结构 | 0.10 | 消息文本特征：长度、结构、Unicode、n-gram |

曾经占 0.40 权重的 embedding 信号，已随支撑它的重型 ML 栈（ONNX Runtime、transformers、
XGBoost）一起移除。它的投票，以及它集中在 MEDIUM 边界上的大部分误差，也一并消失。
模糊的首轮现在交给[路由判定器](#routing-judge)。

结果映射为一个复杂度得分和一个公开档位：**SIMPLE**（低于 0.33）、**MEDIUM**（低于
0.67）或 **COMPLEX**。置信度经过校准，每个决策都记录在日志元数据里
（`routing_complexity`、`routing_confidence`、`routing_reasoning`、
`routing_cost_estimate`、`routing_savings`、`routing_tier`、`resolved_model`）。

## 路由判定器 {#routing-judge}

可选，默认关闭。**路由判定器**是一个 [System One](/zh/api/systemone) 决策模型，路由器在
自身信号拿不准时会咨询它；之后该请求的档位由它的结论决定。设计记录在 ADR-0018
（"A routing judge owns the tier inside the ambiguity band"，见
[仓库内](https://github.com/zwldarren/llm-proxy/blob/main/docs/adr/0018-routing-judge-owns-ambiguous-band.md)）。
运维上需要关注的是：

- 只判定首轮：绝不对后台调用做判定。 判定器看到的是当前这次提问、配置数量的更早
  *用户*轮次以及能力标志——从不包括助手或工具输出。从第二轮起它就是在盲判，所以这些
  轮次仍由信号组合决定。带 OpenResponses `background` 标志的请求同样不判定：客户端是
  轮询取结果而不是等结果，没有可花的延迟预算。
- 默认只对 `auto` 和 `best`。 `fast` 的存在意义就是挑最便宜的有能力模型，判定器
  调用与它相悖。
- 哪些首轮会交给判定器，由一道闸门决定。判定条件可配置：置信度阈值、半开复杂度区间，以及
  `not_low_anchor`（只要信号组合没有把这一轮放在最低锚点——复杂度 `0.0`——就交给判定器）。
  默认全部不开启：先让闸门关着，用影子模式收集数据（ADR-0029）——在修正了信号
  组合的档位高估偏差之后，各次记录下来的语料显示，凡是调用率高的闸门，判定器都不如
  信号组合，所以默认全开会问得更多、收益更少。`not_low_anchor` 和其他条件，是运营者
  在自己的环境里跑完影子结论记录、看到判定器确实占优的区间之后才打开的。限制额外
  延迟和成本的是判定调用率，而不是模型本身。
- 一道消费门槛决定听信哪些结论。 被咨询出的结论并非自动正确：在记录的语料上，
  判定器自信时的结论明显比含糊时更准。设置 `apply_min_confidence`（结论在自己所选档位
  上的概率质量）或 `apply_min_escalation`（升级概率）后，两个门槛都不过的结论会完整
  记录，但档位仍用信号组合的结果（决策推理里记为 `judge-held=`）。两者都不设——默认
  ——则听信每个非弃权的结论。实测起点和"先测量"的提醒见 ADR-0029；评测工具会把各种
  策略与闸门并排报出。
- 下限与上限依然优先。 结论只替换信号组合本会使用的复杂度；视觉、结构化输出、
  最终校验这几项下限以及常规成功上限都在其后应用，与没有判定器时完全一样。
- 拿不到结论时一律退回信号组合：超时、HTTP 错误、无法解析的回答、模型自己给出
  *ambiguous* 回答，或熔断开启。判定器永远不是第四个信号——它不出现在
  `signal_votes` 里，它自己的置信度（衡量答案有多尖锐，而不是有多大概率正确）也绝不
  会成为路由置信度。
- 影子模式（打开判定器时的默认状态）记录判定器本来会说什么，但不做任何改变。它还会
  抽样一小部分闸门**没有**触发的轮次，因为只在闸门内测一致性，无法说明闸门放过了什么。
  等结论足以支撑决策后再关掉影子模式。
- 多一次调用，记在运营者的账上。 被判定的一轮恰好发起一次上游调用，按判定器模型的
  输入 Token 计费。判定器不做预热：启动时不发起任何判定调用，因此 `deadline_s` 必须覆盖
  模型自身的响应时间，包括本地模型在启动后第一个被判定轮次上的冷加载。无法满足的截止
  时间不会大声报错——该轮退回信号组合，`routing.judge.error` 记录原因。
- 每次调用都是独立的一行日志。 判定调用以 `judge` 日志类型落在日志库里：有自己
  的模型、提供商、Token 和成本，并归属到触发它的那个请求——所以判定花费能按模型统计，
  也计入该密钥的花费和预算。它不是客户端发起的请求，因此不计入代理请求数，并在日志里
  拥有独立的 **判定调用** 标签页。它所服务的那个请求则在 `routing.judge` 下保留结论。

在 **设置 → 高级 → 智能路由 → 路由判定器**（`server_config.smart_routing.judge`）
里配置。选择器只列出标记了 **`supports_systemone`** 的模型；先在模型编辑器里给模型打上
这个标记——必须是 System One 模型，且该端点是 chat 专用的。想先衡量候选判定器再决定
是否信任，可以用路由评测工具（`python -m llm_proxy.routing.eval`），它会报告判定器在
人工语料上的准确率、各闸门触发条件对应的调用率，以及延迟分位数。

## 训练数据导出

路由器下一代训练所用的两份语料通过管理 API 以 JSONL 导出
（`GET /api/routing/export/dataset?format=feedback|judge_shadow|all`）：显式反馈标签
（各自带被路由的 prompt 和档位决策），以及判定器记录的结论（各自带它本会替换的信号
组合决策、它自己的分布，以及用户当时给出的信号）。[影子模式](#routing-judge)收集的
就是这些数据（ADR-0029）。prompt 文本会按判定器自己的提问预算截断，因此训练读到的
就是路由器当时看到的内容。

响应是流式分页的：逐批读取并序列化，而不是在内存里拼装；两份语料都按时间升序返回。
超过一页的遍历会用 `since` 取已见的最新时间戳重新发起请求——边界那一行会重复，但遍历
总能前进——`limit` 受每份语料上限（50,000 行）约束。

## 模型如何选出

候选模型必须先通过硬性条件：密钥/用户白名单、上下文长度、图像能力、预算。然后综合
打分：

- 预测成本，基于模型的实际生效定价。
- 档位质量匹配：复杂度到所配置 `quality_tier` 的映射。各模式的质量权重决定质量
  相对成本的分量：`fast 0.35`、`auto 0.65`、`best 1.0`（可配置），并随复杂度上升。
  相对质量门槛会排除低于最佳可用质量 50%（fast）、60%（auto）、85%（best）的候选。
- 经验学习：基于单模型结果（`model_experience`：奖励均值、可靠性、延迟、显式
  反馈、缓存亲和性）的 Thompson 采样 bandit，外加内存中的延迟统计。
- 连续性：同一对话上次使用的模型优先（Redis 键
  `routing:conv:<conversation>:last_model`，TTL 30 分钟）。提供商侧保留的前缀缓存也
  计价：在位模型观测到的缓存亲和性，用来估算有多大比例的输入按缓存读取比例而非全价
  计费，因此切换就要为失去的缓存买单。
- 探索：新模型或采样不足的模型会获得试拉机会；工具/agent 步骤不探索，以保证多步
  流程连贯。

若无模型满足条件，请求以路由约束错误失败——一个结构化的 4xx，携带具体错误码：
`no_available_models`（400，没有支持图像或上下文可行的模型）、`allowlist_exhausted`
（403，撞到密钥的权限边界）、`routing_constraints_unmet`（400），或 `budget_exceeded`
（429 `insufficient_quota`，即显式 `max_cost` 上限）。

开启**优雅降级**（`smart_routing.graceful_degradation`）后，有两项*偏好*会放松而不是
直接失败，决策推理里分别记为 `degraded=...`：让候选池变空的虚拟模型分配会被忽略；当
没有模型能同时装下输入和输出时，只装得下输入 Token 的模型也能承接，由上游截断输出。
图像能力、白名单和预算上限从不放松——这些拒绝本身就是功能。

在对话首轮，如果闸门触发，配置的[路由判定器](#routing-judge)会替换信号在这一步产出的
档位——上面其余选择逻辑不变，所以判定器改变的是请求**从哪个档位**得到服务，而不是档位
内哪个模型胜出。

## 反馈

给决策打分，用来引导后续决策（`POST /api/me/feedback`，或在日志详情页操作）：

| 信号 | 含义 |
| --- | --- |
| `ok` | 选对了模型——强化它 |
| `weak` | 对此请求来说太弱 |
| `strong` | 比需要的更强（质量浪费） |

反馈只对经过智能路由的请求有效：请求未经路由返回 422，已记录过反馈返回 409（每个请求
只能评分一次），非管理员给不属于自己的请求评分返回 404。

## 诊断

在设置 → 高级 → 智能路由里开启**路由诊断**（详细路由日志）后，请求的日志条目还会带上
候选评分卡、信号投票、所用权重和护栏说明。要回答「`auto` 为什么选了这个模型？」这是
最快的办法。每个智能路由请求都带嵌套的 `routing` 块；判定器咨询记录
（`routing.judge`：闸门、影子标志、结论及其分布、延迟、输入 Token、成本及成本来源、
错误）无论是否开启诊断都会记在里面，因此影子上线可以被量化，不必开详细日志。该调用
本身也是 `judge` 日志类型下独立的一行——见[判定调用](/zh/admin/observability)——所以
即使不打开它所服务的请求，也能按模型看到它的 Token 和成本。

各模式权重也在同一节里配置（`fast`/`auto`/`best`）；更底层的调参常量编译在代码里。

## 运维说明

- 虚拟模型**只提供 chat**：embeddings、图像和音频端点会拒绝它们（在路由关闭时使用虚拟
  模型属于配置错误）。
- 解析出具体模型后，白名单会针对**具体**模型重新校验，因此限定到某些模型的密钥仍能用
  `auto`——只是会在自己的白名单范围内路由。
- 对话连续性和粘性提供商状态依赖 Redis；没有 Redis 时，每个请求独立评分。
